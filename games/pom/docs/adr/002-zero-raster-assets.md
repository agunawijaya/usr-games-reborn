# ADR-002: Zero Raster Assets — Every Pixel Comes From Code

- **Status:** Accepted
- **Date:** 2026-09-23
- **Deciders:** Agun Wijaya (repo owner, hard rule in port brief), Claude Opus
- **Scope:** Port-level (`pom` / `fancy-web`)

## Context

Several recent fancy-web ports in this repo reached their look through
**painted raster art**: `trek` uses seven painted nebula backdrops and
PNG ship sprites, `adventure` uses 24 digital paintings, `hangman`
composes 30+ curated PNG/WebP/JPEG references. That works, but it
makes those ports only as good as their art pipeline, and it teaches
little about *how* images are made.

*Selene* exists to prove the opposite point: **a stunning,
photographic scene can be produced purely from code.** The Moon, the
sky and the landscape all have to be generated by maths. The rule
also lines up with the original `pom`, a 285-line C program that
contains its whole universe as seven orbital constants.

This rule needs an ADR because it constrains every future
contribution to this port (and because it deliberately breaks with the
painted-asset convention of sibling ports).

## Options Considered

### Option A — Painted / photographic assets (sibling-port convention)

**Description:** Use a NASA LRO Moon mosaic (public domain) as an
albedo texture, a starfield photo for the sky, and a painted
landscape.

**Pros:**
- Fastest route to a realistic Moon: the real near side, pixel-exact.
- Minimal shader work.

**Cons:**
- Defeats the port's stated purpose (proving code-only graphics).
- A photo has **its own baked-in lighting**. The LRO mosaics are shot
  near full illumination, so relighting them for a crescent gives
  a flat, "sticker" look at the terminator: no shadows, no rim
  highlights. That is exactly what the brief calls fake.
- Adds multi-megabyte downloads and licensing/attribution burden.

**Suitable when:** the goal is fidelity to real imagery, not
demonstration of technique.

### Option B — Hybrid: code for lighting, small raster lookup textures

**Description:** Procedural shaders, but ship a few small helper
rasters: a blue-noise PNG for dithering, a baked height map, a
gradient LUT.

**Pros:**
- Blue-noise and LUT PNGs are standard real-time graphics practice.
- Saves some start-up compute.

**Cons:**
- Blurs the rule. "Just one small PNG" is how rules erode, and a
  reviewer can no longer check compliance with a single `grep`.
- Every one of those textures can be generated at start-up in
  milliseconds anyway.

**Suitable when:** start-up time or GPU budget is critical (mobile
games). Not our constraint.

### Option C — Strict zero-raster in `src/` (chosen)

**Description:** No PNG / JPG / JPEG / WebP / GIF / AVIF / BMP / ICO /
TIFF files anywhere under `src/`. No base64 raster `data:` URIs
either. Every pixel is produced at runtime by:
- WebGL2 / GLSL shaders (Moon surface bake, lighting, sky, stars,
  Milky Way, landscape),
- procedural noise (hash-based value / cellular / fbm),
- Canvas 2D (only as a *destination* for shader-rendered mini Moons),
- SVG / CSS (UI glyphs and typography).

GPU render targets produced at runtime from those sources (e.g. the
baked surface texture) are permitted, since they are generated by code.

**Pros:**
- The port *is* its own proof: view-source shows the whole world.
- Tiny payload. The whole port is a few hundred KB of text.
- Rule is mechanically checkable (an automated test enforces it).
- Forces physically-motivated lighting, which reads as more real at
  the terminator than a relit photo would.

**Cons:**
- The Moon is *procedurally plausible*, not a photographic copy of the
  real near side. Mitigated by placing the major maria and
  named craters at their real selenographic coordinates (a small
  table of ~40 numbers), so the familiar "face" of the Moon is
  recognisable.
- Start-up bake cost (tens to hundreds of ms on a GPU).

## Decision

**We chose Option C — strict zero-raster assets in `src/`.**

Scope of the rule:

| Location | Raster allowed? |
|---|---|
| `src/**` (all runtime code and assets) | ❌ **Never** |
| `index.html` (the page shell) | ❌ Never (favicon is inline SVG) |
| `media/` (port screenshots for README) | ✅ Yes — documentation, not runtime |
| `tests/fixtures/` | ✅ Text only in practice (golden output JSON) |
| Web fonts from Google Fonts | ✅ Vector glyph outlines, not raster |

Enforcement: `tests/zero-raster.test.js` walks `src/` and
`index.html`, fails on any raster file extension, any
`data:image/(png|jpe?g|webp|gif|avif|bmp)` URI, and any `url(...)`
or `src=` reference to a raster extension.

## Consequences

### Positive

- The port is a self-contained lesson in procedural rendering: every
  crater traces back to a hash function and a table row.
- Changing the Moon's look is a matter of editing numbers, not
  re-painting.
- Screenshots are reproducible bit-for-bit (seeded procedural
  generation).

### Negative / Risks

- More shader code than an asset-driven approach, so there are more
  places to get realism wrong. Mitigated by an explicit art-direction
  critique loop in the diff-log (screenshot → critique → fix).
- Contributors must not "just drop in" a texture. PRs doing so fail
  the test suite by design.

### Follow-on Work

- None required. If a future contributor wants a photographic Moon,
  that is a different port (`fancy-web-lro`), not a change to this
  one.
